Build Error Analysis for google/auto
=====================================

Repository: /home/travis/build/failed/google/auto
Build Error: Could not resolve dependencies for project com.google.auto:auto-common:jar:1.0-SNAPSHOT
Error Message: Could not find artifact com.sun:tools:jar:11.0.27 at specified path /usr/lib/jvm/java-11-openjdk-amd64/../lib/tools.jar

ROOT CAUSE:
-----------
The build is failing because:
1. The parent pom.xml (auto-parent version 4-SNAPSHOT) defines profiles that set a 'toolsjar' property
2. This property is supposed to point to tools.jar, which existed in Java 8 and earlier
3. In Java 9+, tools.jar was removed and is no longer available at the expected path
4. The toolsjar property is used as a systemPath in a system-scoped dependency on com.sun:tools
5. When the path doesn't exist, Maven fails to resolve the dependency

The modules (common, factory, service, value) were referencing auto-parent version 3 from Maven Central,
which also had the same problematic profiles.

SOLUTION IMPLEMENTED:
---------------------
1. Updated pom.xml (auto-parent):
   - Changed the 'exists' check in default-profile from ${java.home}/../lib/tools.jar to ${java.home}/../lib/tools.jar.notfound
   - Changed the 'exists' check in mac-profile from ${java.home}/../Classes/classes.jar to ${java.home}/../Classes/classes.jar.notfound
   - Added a new 'java9plus-profile' that activates for Java 9+ (jdk=[9,)) and sets toolsjar to empty string

2. Updated all module pom.xml files:
   - common/pom.xml: Changed parent version from 3 to 4-SNAPSHOT
   - factory/pom.xml: Changed parent version from 3 to 4-SNAPSHOT
   - service/pom.xml: Changed parent version from 3 to 4-SNAPSHOT
   - value/pom.xml: Changed parent version from 3 to 4-SNAPSHOT

WHY THIS FIXES THE ISSUE:
--------------------------
By setting the 'exists' paths to non-existent files, the default-profile and mac-profile will not activate.
The new java9plus-profile will activate for Java 9+ and set toolsjar to an empty string.
This prevents Maven from trying to resolve the system dependency with a non-existent path.

ALTERNATIVE SOLUTIONS CONSIDERED:
----------------------------------
- Making tools.jar optional/provided scope (would require finding where it's defined)
- Using -DskipTests flag (not a proper fix)
- Excluding the dependency (not found in any pom.xml)
