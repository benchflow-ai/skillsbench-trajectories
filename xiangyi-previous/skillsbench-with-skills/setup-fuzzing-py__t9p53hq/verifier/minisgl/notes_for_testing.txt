FUZZ TESTING NOTES FOR MINISGL LIBRARY
=======================================

TARGET LIBRARY: minisgl (LLM inference framework)
Main Purpose: Lightweight high-performance inference framework for Large Language Models (LLMs)

PRIMARY FUZZ TARGETS:
======================

1. serialize_type(obj) / deserialize_type(data_dict)
   - File: /app/minisgl/python/minisgl/message/utils.py
   - Input: Python objects (dataclasses, tensors, dicts) / JSON-serialized dicts
   - Output: Serialized JSON data / Deserialized Python objects
   - Why fuzz: Handles arbitrary Python object serialization across process boundaries
   - Fuzzing focus:
     * Complex nested dataclass structures
     * Tensor shape/dtype variations
     * Circular references / self-referential objects
     * Extreme numeric values (inf, nan, very large numbers)
     * Unicode strings in dataclass fields
     * Type mismatches in deserialization
     * Missing/extra keys in dicts
     * Invalid JSON structures
     * Corrupted base64 tensor data

2. TokenizeManager.tokenize(text, mode='v1')
   - File: /app/minisgl/python/minisgl/tokenizer/tokenize.py (line ~50)
   - Input: Chat messages, text strings, or prompt lists
   - Output: Token ID tensors (int32 arrays)
   - Why fuzz: Parses user input and applies chat templates
   - Fuzzing focus:
     * Very long text inputs (>1M tokens)
     * Chat template injection / special characters
     * Unicode edge cases (emoji, CJK characters)
     * Empty messages or null messages
     * Invalid message roles
     * Mixed text/image/video content types
     * Deeply nested message lists
     * Non-ASCII characters in prompts

3. DetokenizeManager.detokenize(token_ids, input_len, output_len)
   - File: /app/minisgl/python/minisgl/tokenizer/detokenize.py (line ~80)
   - Input: Token ID arrays + length parameters
   - Output: Decoded text strings
   - Why fuzz: Converts tokens back to text with CJK character detection
   - Fuzzing focus:
     * Invalid token IDs (out of vocabulary)
     * Token ID bounds checking
     * CJK character boundary edge cases
     * Streaming mode state management
     * Invalid length parameters
     * Buffer overflow in token sequences
     * Unicode combining characters
     * BOM (byte order mark) handling

4. Sampler.sample(logits, sampling_params, num_samples)
   - File: /app/minisgl/python/minisgl/engine/sample.py (line ~100)
   - Input: Logit arrays + SamplingParams + sample count
   - Output: Sampled token IDs
   - Why fuzz: Numeric computation with softmax, top-k, top-p
   - Fuzzing focus:
     * NaN/Inf in logits
     * Extreme temperature values (0, negative, very large)
     * Top-k > vocabulary size
     * Top-p outside [0, 1]
     * Softmax numerical stability edge cases
     * Empty logit arrays
     * Single value logits
     * Very large or very small logit values

5. Req state management (Req.append_host, complete_one, can_decode)
   - File: /app/minisgl/python/minisgl/core.py (line ~80+)
   - Input: Request state (input_ids, cached_len, output_len)
   - Output: Modified request state or boolean
   - Why fuzz: State machine for request lifecycle
   - Fuzzing focus:
     * Invalid state transitions
     * Negative lengths / out-of-bounds indices
     * Integer overflow in position tracking
     * Empty input sequences
     * cached_len > output_len boundary cases
     * Max token length violations

6. PrefillAdder._try_allocate_one(Req)
   - File: /app/minisgl/python/minisgl/scheduler/prefill.py (line ~150)
   - Input: Request object + scheduler state
   - Output: Boolean (allocation success/failure)
   - Why fuzz: Memory allocation logic for prompt processing
   - Fuzzing focus:
     * Requests with huge prompt lengths
     * Cache fragmentation scenarios
     * Integer overflow in page calculations
     * Out-of-memory conditions
     * Concurrent allocation edge cases

MESSAGE SERIALIZATION DATA STRUCTURES:
=======================================
Key types in /app/minisgl/python/minisgl/message/:
- TokenizeMsg: input, mode, priority
- DetokenizeMsg: token_ids, input_len, output_len
- UserMsg: input_ids, sampling_params
- UserReply: next_token, finish, error
- SamplingParams: temperature, top_k, top_p, ignore_eos, max_tokens

ORACLE PROPERTIES:
===================
1. Serialization round-trip: serialize(obj) → deserialize() == obj (structurally)
2. Tokenization determinism: same input → same tokens
3. Detokenization produces valid UTF-8
4. Sampling produces valid token IDs within vocabulary range
5. No panics/hangs on malformed input
6. Request state transitions follow valid sequences
7. Memory allocation doesn't exceed system limits

SEED CORPUS IDEAS:
===================
- Basic text: "hello", "world", short prompts
- Chat messages: [{"role": "user", "content": "..."}]
- Unicode text: "你好世界", "🎉 emoji test", "café"
- Long prompts: 10k, 100k, 1M token sequences
- CJK edge cases: mixed Chinese/Japanese/Korean
- Special characters: \n, \t, \r, null bytes
- Token boundaries: max token ID, 0, negative IDs
- Sampling params: temp=0, temp=2, top_k=1, top_p=0.9
- Extreme values: very large arrays, empty arrays
- Invalid structures: missing keys, wrong types

IMPORTANT DETAILS:
===================
- Vocabulary size: Model-dependent (typically 32k-128k)
- Max sequence length: Model-dependent (typically 4k-200k)
- Token IDs: Non-negative integers
- Logits: Float values (can be inf/nan)
- Temperature: Positive float (0 = greedy, higher = more random)
- Top-k: Non-negative integer
- Top-p: Float in [0, 1]
- Process architecture: Multi-process (frontend, tokenizer, scheduler, detokenizer)
- Communication: ZMQ message passing

DEPENDENCIES:
==============
- torch: Tensor operations
- transformers: Model loading, chat templates
- numpy: Numerical operations
- zmq: Message passing
- double-conversion: Float serialization
