FUZZ TESTING NOTES FOR BLACK LIBRARY
=====================================

TARGET LIBRARY: black (Python code formatter)
Main Purpose: Automatically reformats Python code to conform to Black's opinionated style

PRIMARY FUZZ TARGETS:
======================

1. lib2to3_parse(src_txt, target_versions)
   - File: /app/black/src/black/parsing.py (line ~55)
   - Input: Arbitrary Python source code + target version set
   - Output: lib2to3 parse tree (Node/Leaf objects)
   - Why fuzz: Core Python parser with version-specific grammar handling
   - Fuzzing focus:
     * Invalid Python syntax edge cases
     * Version-specific syntax (f-strings, match statements, type params)
     * Deep nesting (deeply nested parens, brackets, braces)
     * Very long identifiers/strings
     * Mixed encoding declarations and unicode
     * Invalid escape sequences
     * Malformed type annotations
     * Edge cases in async/await syntax

2. format_str(src_contents, mode, lines)
   - File: /app/black/src/black/__init__.py (line ~1177)
   - Input: Python source string + Mode configuration + optional line ranges
   - Output: Formatted Python code string
   - Why fuzz: End-to-end formatting with validation checks
   - Fuzzing focus:
     * Mode configuration edge cases (extreme line lengths, all flags)
     * Code with complex nesting
     * String formatting interactions (quotes, escapes, f-strings)
     * Comment preservation in edge cases
     * Trailing comma handling
     * Operator spacing edge cases
     * Decorator handling

3. parse_ast(src)
   - File: /app/black/src/black/parsing.py (line ~137)
   - Input: Python source code string
   - Output: Python AST object or SyntaxError
   - Why fuzz: AST parsing across Python versions
   - Fuzzing focus:
     * Type comment edge cases
     * Invalid type annotations
     * Complex decorator expressions
     * Walrus operator edge cases
     * Match statement syntax (Python 3.10+)
     * Type parameters (Python 3.12+)

4. assert_equivalent(src_before, src_after)
   - File: /app/black/src/black/__init__.py (line ~1581)
   - Input: Original source + formatted source
   - Output: None (no exception) or AssertionError
   - Why fuzz: Validates semantic equivalence after formatting
   - Fuzzing focus:
     * Edge cases that might break equivalence detection
     * Code with unusual but valid AST patterns
     * Comments with code-like content

5. LineGenerator visitor methods (class traversal)
   - File: /app/black/src/black/linegen.py (line ~400+)
   - Input: Parse tree nodes + Mode
   - Output: Formatted Line objects
   - Why fuzz: Complex AST traversal with transformation logic
   - Fuzzing focus:
     * All Python syntax node types
     * Complex nested structures
     * Edge cases in parenthesis handling

MODE CONFIGURATION PARAMETERS:
===============================
- line_length: 88 (default), but test with extremes (1, 10000)
- target_versions: {PY33, PY34, ..., PY314}
- string_normalization: True/False
- is_pyi: True/False (stub files)
- is_ipynb: True/False (Jupyter notebooks)
- magic_trailing_comma: True/False
- preview: True/False

ORACLE PROPERTIES:
===================
1. Idempotency: format(format(code)) == format(code)
2. Equivalence: AST(format(code)) == AST(code)
3. No panics/hangs on any input
4. Output is valid Python syntax
5. Determinism: Same input always produces same output
6. Preserves newlines in comments and docstrings

SEED CORPUS IDEAS:
===================
- Simple statements: x = 1, def f(): pass
- Complex nesting: ((((x))))
- String variations: "str", 'str', f"str", r"str", b"str"
- Operators: x + y, x ** y, x := y
- Decorators: @decorator, @decorator.attr, @decorator()
- Type annotations: def f(x: int) -> str: pass
- Match statements: match x: case 1: pass
- Async code: async def f(): await x
- Comments: # comment, """ doc """, ''' doc '''
- Long lines: x = "very long string" * 100
- Invalid syntax: should not crash but may raise SyntaxError
