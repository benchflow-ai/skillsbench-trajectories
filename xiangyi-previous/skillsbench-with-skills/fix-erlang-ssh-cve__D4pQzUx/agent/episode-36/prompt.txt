# Erlang/OTP SSH Unauthenticated Remote Command Execution Vulnerability Fix

## Vulnerability Description

A critical vulnerability was discovered in the Erlang/OTP SSH server that allows attackers to execute arbitrary system commands remotely WITHOUT authentication.

### Root Cause

The vulnerability exists in `lib/ssh/src/ssh_connection_handler.erl`. The SSH connection handler processes SSH connection protocol messages (wrapped as `conn_ms
g` events) in ANY state of the connection state machine, including states BEFORE user authentication is complete.

### Attack Vector

An attacker can:
1. Initiate an SSH connection to the server
2. Before completing authentication, send SSH protocol messages such as:
   - `SSH_MSG_CHANNEL_REQUEST` with type "exec" to execute commands
   - `SSH_MSG_CHANNEL_REQUEST` with type "shell" to open a shell
   - `SSH_MSG_CHANNEL_REQUEST` with type "subsystem" to start subsystems
3. These messages are processed by `ssh_connection:handle_msg()` which calls `handle_cli_msg()`
4. The `handle_cli_msg()` function starts a CLI process and executes the requested command
5. No authentication check is performed before command execution

### Affected Code Path

1. SSH messages are decoded in `handle_event()` around line 1187
2. `SSH_MSG_CHANNEL_REQUEST` messages are wrapped as `{conn_msg, Msg}`
3. The `handle_event(internal, {conn_msg,Msg}, StateName, ...)` clause at line 771 processes these messages
4. This handler calls `ssh_connection:handle_msg()` regardless of the `StateName`
5. For "exec" requests, this eventually calls `handle_cli_msg()` in `ssh_connection.erl`
6. Commands are executed without verifying that authentication has completed

## Fix Implementation

### Location
File: `lib/ssh/src/ssh_connection_handler.erl`
Lines: 760-769 (new authentication check clause)

### Fix Description

Added a new `handle_event` clause that intercepts `conn_msg` events when the connection is NOT in an authenticated state:

```erlang
%% Reject connection messages before authentication is complete
%% This clause catches conn_msg in non-connected states (except during renegotiation)
handle_event(internal, {conn_msg,_Msg}, StateName, D)
  when StateName =/= {connected,client}, StateName =/= {connected,server},
       StateName =/= {kexinit,client,renegotiate}, StateName =/= {kexinit,server,renegotiate},
       StateName =/= {ext_info,client,renegotiate}, StateName =/= {ext_info,server,renegotiate} ->
    %% Connection messages should only be processed after successful authentication
    Disconnect = #ssh_msg_disconnect{code = ?SSH_DISCONNECT_PROTOCOL_ERROR,
                                      description = "Connection message received before authentication"},
    {Repls, D1} = send_replies([{connection_reply, Disconnect}], D),
    {stop_and_reply, {shutdown, "Protocol error"}, Repls, D1};
```

### How the Fix Works

1. **Pattern Matching**: The new clause matches `conn_msg` events before the original handler
2. **State Validation**: Uses guard clauses to check if the state is NOT one of:
   - `{connected,client}` - authenticated client
   - `{connected,server}` - authenticated server
   - `{kexinit,client,renegotiate}` - client renegotiating keys
   - `{kexinit,server,renegotiate}` - server renegotiating keys
   - `{ext_info,client,renegotiate}` - client in ext_info during renegotiation
   - `{ext_info,server,renegotiate}` - server in ext_info during renegotiation
3. **Rejection**: If in an unauthenticated state, sends `SSH_DISCONNECT_PROTOCOL_ERROR` and closes the connection
4. **Fallthrough**: If authenticated or renegotiating, the message falls through to the original handler (line 771)

### Security Impact

- **Before Fix**: Attackers could execute arbitrary commands without authentication
- **After Fix**: Connection messages (exec, shell, subsystem) are ONLY processed after successful authentication
- **Normal Operation**: Legitimate authenticated sessions continue to work normally
- **Renegotiation**: Key renegotiation during active sessions continues to work correctly

## Verification

The fix ensures that:
1. Unauthenticated SSH_MSG_CHANNEL_REQUEST messages are rejected
2. The server responds with SSH_DISCONNECT_PROTOCOL_ERROR
3. The connection is terminated before any command execution
4. Authenticated sessions can still execute commands normally
5. SSH key renegotiation continues to function properly
