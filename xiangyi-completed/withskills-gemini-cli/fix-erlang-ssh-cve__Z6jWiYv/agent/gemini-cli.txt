The vulnerability allowed attackers to execute arbitrary system commands by sending `SSH_MSG_CHANNEL_REQUEST` with "exec" (wrapped in a connection layer message) before authentication was completed. I modified `otp_src_27.3.2/lib/ssh/src/ssh_connection_handler.erl` to check the connection state before processing `conn_msg` events.
If the session is not yet in a connected state (or re-negotiating), the message is now **postponed** using `{keep_state_and_data, postpone}`. This ensures that:
1.  The command is not executed before authentication.
2.  If the user successfully authenticates later, the postponed messages are replayed and processed lawfully.
3.  If authentication fails, the commands are never executed.

This prevents the unauthenticated command execution while maintaining correct behavior for authenticated users.

**Summary of the Fix:**

The issue was that the `ssh_connection_handler` process was handling `conn_msg` events (which include `SSH_MSG_CHANNEL_REQUEST` for "exec") regardless of whether the SSH session had been authenticated. This allowed an attacker to send an "exec" request immediately after the transport layer was established but before authentication, triggering the execution of the command.

I modified the `handle_event` function for `{conn_msg, Msg}` to explicitly check if the session is in a "connected" state (which implies successful authentication) or is re-negotiating.
