The critical vulnerability allowing unauthenticated remote command execution in the Erlang/OTP SSH server has been identified and fixed.

### Analysis
The vulnerability existed in `ssh_connection_handler.erl`. The handler for internal connection messages (`{conn_msg, Msg}`) processed incoming SSH Connection Protocol messages (such as `ssh_msg_channel_request` for "exec") regardless of the current state of the connection (e.g., during `hello` or `userauth` phases).

While the handler attempted to filter *replies* based on the connection state (queuing some replies if not connected), `ssh_connection:handle_msg/4` was still executed. For "exec" requests, `ssh_connection:handle_msg/4` calls `handle_cli_msg/3`, which immediately spawns a process to execute the command via `start_cli/2`. This side effect occurred before the reply filtering logic could intervene, allowing an attacker to execute commands by sending a crafted `SSH_MSG_CHANNEL_REQUEST` packet before completing authentication.

### Fix
The fix involves modifying `ssh_connection_handler:handle_event/4` to explicitly check if the connection is in a `connected` state or in `renegotiation` before processing any `{conn_msg, Msg}`. If the connection is not yet established (e.g., during the authentication phase), the event is postponed. This ensures that `ssh_connection:handle_msg/4`—and strictly the command execution logic—is never invoked until the user is fully authenticated.
