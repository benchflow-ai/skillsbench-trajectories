I have addressed the remote code execution vulnerability in Apache Druid 0.20.0.

### Vulnerability Analysis
The vulnerability allowed authenticated attackers to execute arbitrary code via malicious JavaScript payloads. The exploit leveraged an empty key `""` in the JSON request to bypass JavaScript security settings. This happened because Jackson's `@JacksonInject` was matching the empty property name from the JSON input, overriding the secure configuration injected by the system.

### Fix Implemented
I implemented a two-layered defense:
1.  **Global Fix in `GuiceAnnotationIntrospector`**: Modified the custom annotation introspector to explicitly set `useInput = false` for all `@JacksonInject` annotations. This prevents Jackson from ever using JSON input to satisfy these injected values, which is the standard security practice in Druid for Guice-injected components.
2.  **Specific Fixes in JavaScript-related classes**: For all 7 classes identified as using `JavaScriptConfig`, I updated the constructors to:
    *   Add an explicit `@JsonProperty("config")` to the injected parameter to give it a name other than the default empty string.
    *   Explicitly set `useInput = OptBoolean.FALSE` on the `@JacksonInject` annotation as a secondary defense.

Classes patched:
*   `JavaScriptDimFilter`
*   `JavaScriptExtractionFn`
*   `JavaScriptAggregatorFactory`
*   `JavaScriptPostAggregator`
*   `JavaScriptParseSpec`
*   `JavaScriptWorkerSelectStrategy`
*   `JavaScriptTieredBrokerSelectorStrategy`

### Verification
I created a unit test `JavaScriptDimFilterExploitTest` that reproduced the vulnerability by showing that a malicious JSON payload with `"": {"enabled": true}` could enable JavaScript even when it was globally disabled. After applying the fixes, the test confirmed that the exploit is blocked and JavaScript remain disabled as expected. Legitimate requests continue to work when JavaScript is explicitly enabled in the configuration.
