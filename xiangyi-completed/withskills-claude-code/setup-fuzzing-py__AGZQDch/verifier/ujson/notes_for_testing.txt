UJSON LIBRARY - FUZZING TARGET ANALYSIS
================================================================================

## Library Overview
UltraJSON (ujson) is an ultra-fast JSON encoder and decoder written in C with
Python bindings. It's designed for high performance but has known security
concerns - the README explicitly warns that it's "fundamentally ill-suited to
making changes without risk of introducing new security vulnerabilities."

**CRITICAL: This is a prime fuzzing target due to:**
- C implementation with manual memory management
- Known security history (buffer overflows mentioned)
- Parses untrusted JSON input
- Native extension boundary

## 3. EXISTING UNIT TEST SUMMARY
================================================================================

### Test Coverage Map:
- test_ujson.py: Extensive tests
  - JSON parsing for all types (null, bool, int, float, string, array, object)
  - Unicode handling
  - Large numbers, infinity, NaN
  - Nested structures
  - Edge cases and error conditions
  - Encoding options (escape_forward_slashes, ensure_ascii, etc.)

- fuzz.py: Existing fuzzing harness!
  - Already has fuzzing infrastructure
  - Tests loads() with random data

- sample.json, 334-reproducer.json: Test data
  - Specific edge cases and bug reproducers

### Inferred Oracles:
1. No-crash: Invalid JSON should raise ValueError, not crash/segfault
2. Round-trip: loads(dumps(obj)) == obj (for JSON-compatible types)
3. Deterministic: Same input always produces same output
4. Spec compliance: Valid JSON should parse correctly
5. Memory safety: No buffer overflows, use-after-free, or leaks

### Coverage Gaps (CRITICAL for fuzzing):
1. Extremely large JSON strings (>100MB)
2. Deeply nested structures (>1000 levels) - DoS/stack overflow
3. Very long string keys/values
4. Edge numeric values (max/min int64, special floats)
5. Malformed UTF-8 in strings
6. Invalid escape sequences
7. Truncated JSON (incomplete objects/arrays)
8. Mixed valid/invalid JSON patterns
9. Special Unicode characters (surrogates, null bytes)
10. Pathological number formats (many decimal places, extreme exponents)

## 4. SELECTED FUNCTIONS UNDER TEST (FUTs)
================================================================================

### FUT #1: ujson.loads()

**Why this target:**
- CRITICAL SECURITY BOUNDARY
- C implementation parsing untrusted input
- Known history of buffer overflow vulnerabilities
- Direct attack surface for malicious JSON
- Core functionality of the library

**Callable contract:**
- Required imports: import ujson
- Initialization: None
- Preconditions: Bytes or string input
- Determinism: Deterministic
- External dependencies: None (native C extension)

**Input model:**
- Primary payload: JSON string (bytes or str)
- Constraints: Should be valid JSON (but fuzz invalid too!)
- Edge classes to emphasize:
  - Valid JSON: all types, nested structures
  - Invalid JSON: syntax errors, truncated input
  - Large inputs: >1MB, >10MB, >100MB
  - Deep nesting: >100, >1000, >10000 levels
  - Long strings: >1MB string values
  - Edge numbers: max int64, min int64, huge floats
  - Unicode: all UTF-8 ranges, surrogates, null bytes
  - Escape sequences: \\uXXXX, \\x, invalid escapes
  - Empty input, whitespace-only
  - Binary data (not valid UTF-8)

**Oracles:**
- Must-hold: No segfault, no buffer overflow, no memory leak
- Acceptable: ValueError for invalid JSON
- Suspicious: Any crash, hang, or uncaught exception
- Memory oracle: Run under AddressSanitizer (ASAN) or similar
- Strategy: Crash-only + memory safety fuzzing

**Harness plan:**
- Approach: atheris + LibFuzzer with ASAN
- Minimal harness:
  ```python
  def TestOneInput(data):
      try:
          ujson.loads(data)
      except ValueError:
          pass  # Expected for invalid JSON
      except Exception as e:
          raise  # Unexpected exception
  ```
- Seed corpus:
  - tests/sample.json
  - tests/334-reproducer.json
  - Valid JSON examples (objects, arrays, primitives)
  - JSON test suite (JSONTestSuite)
- Compilation: Build with ASAN enabled
- Timeouts: 10 seconds (parsing should be fast)
- Resource limits: Memory limit to prevent DoS

**Risk flags:**
- Native extension: YES (C code)
- Potential DoS: YES (deep nesting, large inputs)
- Memory unsafety: YES (manual memory management in C)
- External I/O: NO

**Next actions:**
1. Check if existing fuzz.py can be adapted
2. Create atheris harness for ujson.loads
3. Build ujson with ASAN
4. Extract seed corpus from tests
5. Run fuzzer with memory sanitizers


### FUT #2: ujson.dumps()

**Why this target:**
- C implementation with encoding logic
- Recursive serialization can cause stack issues
- Circular reference detection
- Numeric edge cases in encoding

**Callable contract:**
- Required imports: import ujson
- Initialization: None
- Preconditions: Python object (any type)
- Determinism: Mostly deterministic (dict order in Python 3.7+)
- External dependencies: None

**Input model:**
- Primary payload: Create Python objects from fuzzer data
- Approach: Use loads() to create objects, then dumps() them
- Or: Structured fuzzing to build Python objects
- Edge classes:
  - Deep nesting
  - Circular references
  - Large containers (lists, dicts with many elements)
  - All Python types (str, int, float, bool, None, list, dict)
  - Special floats (inf, -inf, nan)

**Oracles:**
- Must-hold: No crash, no infinite loop
- Acceptable: OverflowError for circular references
- Suspicious: Segfault, hang, memory corruption

**Harness plan:**
- Two-stage fuzzing:
  1. Fuzz loads() first to get objects
  2. Then dumps() those objects
- Round-trip testing: loads(dumps(loads(data)))

**Risk flags:**
- Native extension: YES
- Potential DoS: YES (stack overflow on deep recursion)
- Circular ref handling: YES

**Next actions:**
1. Create harness combining loads/dumps
2. Test deep nesting and circular references
3. Run with ASAN
