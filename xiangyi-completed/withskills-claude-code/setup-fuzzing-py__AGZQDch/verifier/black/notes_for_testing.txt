BLACK LIBRARY - FUZZING TARGET ANALYSIS
================================================================================

## Library Overview
Black is "the uncompromising Python code formatter" - it parses Python source code,
builds an AST, and reformats it according to a strict style guide. It uses lib2to3
for parsing and performs complex transformations on the syntax tree.

## 3. EXISTING UNIT TEST SUMMARY
================================================================================

### Test Coverage Map:
- test_black.py: Extensive integration tests (124KB file)
  - format_str() with various Python constructs
  - Edge cases: complex expressions, strings, comments
  - Error handling for invalid syntax
  - Command-line interface tests
  - Configuration file parsing

- test_format.py: Format-specific tests
  - Formatting correctness checks
  - Idempotence testing

- test_ipynb.py: Jupyter notebook formatting
  - Cell validation
  - Magic command handling
  - JSON structure tests

- test_tokenize.py: Tokenization tests
  - Token parsing edge cases

- test_trans.py: Transformation tests
  - String transformations
  - Line transformations

- data/: Large corpus of test Python files
  - Various Python syntax features
  - Edge cases and corner cases

### Inferred Oracles:
1. Idempotence: format_str(format_str(code)) == format_str(code)
2. No-crash: Invalid Python should raise InvalidInput, not crash
3. Deterministic: Same input always produces same output
4. Valid output: Formatted code must be syntactically valid Python
5. AST equivalence: AST of input ≈ AST of output (modulo formatting)
6. No data loss: Formatting should preserve code semantics

### Coverage Gaps:
1. Extremely large Python files (>10MB)
2. Deeply nested expressions (>100 levels)
3. Pathological string literals (very long, many escapes)
4. Malformed UTF-8 in source files
5. Edge cases in Python 3.10+ pattern matching syntax
6. Invalid TOML configuration files
7. Malicious Jupyter notebook JSON structures
8. Files with mixed encodings or encoding declaration mismatches
9. Source files with null bytes or other control characters
10. Combinations of rare Python syntax features

## 4. SELECTED FUNCTIONS UNDER TEST (FUTs)
================================================================================

### FUT #1: lib2to3_parse()

**Why this target:**
- Critical parsing boundary accepting untrusted Python source
- Multiple grammar attempts with complex error handling
- Used by all formatting operations
- Potential for parser bugs, hangs, or crashes
- Core security/robustness target

**Callable contract:**
- Required imports: from black.parsing import lib2to3_parse
- Initialization: None (function call only)
- Preconditions: String input, optional target_versions set
- Determinism: Deterministic
- External dependencies: blib2to3 library (bundled)

**Input model:**
- Primary payload: Python source code string
- Secondary: target_versions (optional Collection[TargetVersion])
- Constraints: Must end with newline (added if missing)
- Edge classes to emphasize:
  - Valid Python code (all versions)
  - Syntactically invalid Python
  - Very long lines (>10000 chars)
  - Deeply nested expressions
  - All Python syntax features (async, pattern matching, etc.)
  - Edge tokens (unusual operators, string prefixes)
  - Files with encoding issues
  - Empty strings, whitespace-only

**Oracles:**
- Must-hold: Returns Node or raises InvalidInput
- Acceptable: InvalidInput for unparseable code
- Suspicious: Any other exception, hangs, crashes, infinite loops
- Strategy: Crash-only + exception type checking

**Harness plan:**
- Approach: atheris-based LibFuzzer harness
- Minimal signature: fuzz(data) -> lib2to3_parse(data.decode('utf-8', 'ignore'))
- Seed corpus:
  - Extract from tests/data/ directory
  - Python stdlib module samples
  - Valid Python snippets from test_black.py
- Timeouts: 5 seconds (parsing can be slow)
- Resource limits: Standard

**Risk flags:**
- Native extension: No (pure Python + blib2to3)
- Potential DoS: Yes (slow parsing on pathological input)
- External I/O: No

**Next actions:**
1. Create atheris harness for lib2to3_parse
2. Extract seed corpus from tests/data/
3. Run fuzzer for 10 seconds
4. Monitor for InvalidInput vs other exceptions


### FUT #2: format_str()

**Why this target:**
- Main public API accepting source code
- End-to-end formatting pipeline
- Higher-level target catching integration bugs
- Tests both parsing and transformation logic

**Callable contract:**
- Required imports: import black; from black import Mode
- Initialization: mode = Mode() (default)
- Preconditions: String input
- Determinism: Deterministic
- External dependencies: None beyond black itself

**Input model:**
- Primary payload: Python source code string
- Secondary: Mode configuration (use defaults for fuzzing)
- Edge classes: Same as lib2to3_parse plus:
  - Code that triggers specific transformations
  - Comments and docstrings
  - String literals with various quotes

**Oracles:**
- Must-hold: Returns formatted string or raises InvalidInput/NothingChanged
- Idempotence: format_str(format_str(x)) == format_str(x)
- Acceptable: InvalidInput for invalid Python
- Suspicious: Other exceptions, crashes

**Harness plan:**
- Two-stage fuzzing:
  1. Fuzz with default Mode
  2. Optionally fuzz Mode parameters
- Check idempotence property
- Verify output is valid Python (can be parsed)

**Risk flags:**
- Potential DoS: Yes (complex transformations)
- External I/O: No

**Next actions:**
1. Create harness wrapping format_str
2. Add idempotence check
3. Optionally parse output to verify validity
4. Use same seed corpus as lib2to3_parse


### FUT #3: parse_pyproject_toml()

**Why this target:**
- Parses user-controlled configuration files
- TOML parsing boundary
- Configuration injection potential
- Different input type (TOML vs Python)

**Callable contract:**
- Required imports: from black.files import parse_pyproject_toml
- Initialization: Needs file path
- Preconditions: Valid file path
- Determinism: Deterministic
- External dependencies: tomli/tomllib library

**Input model:**
- Primary payload: TOML file content (write to temp file)
- Edge classes:
  - Valid pyproject.toml for black
  - Invalid TOML syntax
  - Malformed configuration keys
  - Extremely large TOML files
  - Unicode in configuration

**Oracles:**
- Must-hold: Returns dict or raises OSError/TOMLDecodeError
- Acceptable: OSError, tomli.TOMLDecodeError
- Suspicious: Other exceptions

**Harness plan:**
- Write fuzzer data to temporary file
- Call parse_pyproject_toml with temp file path
- Clean up temp file after each iteration

**Risk flags:**
- File I/O: Yes (requires temp file)
- Potential DoS: TOML parser complexity

**Next actions:**
1. Create harness with temp file handling
2. Seed with valid pyproject.toml examples
3. Fuzz TOML structure
