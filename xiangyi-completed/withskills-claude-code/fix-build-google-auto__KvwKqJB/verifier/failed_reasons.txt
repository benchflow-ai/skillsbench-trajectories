BUILD FAILURE ANALYSIS FOR google/auto REPOSITORY
=================================================

Repository: /home/travis/build/failed/google/auto
Build Command: mvn -f build-pom.xml clean install

ERROR SUMMARY:
--------------
Build failed at module: Auto Common Libraries (auto-common)
Error Message: Could not find artifact com.sun:tools:jar:11.0.27 at specified path /usr/lib/jvm/java-11-openjdk-amd64/../lib/tools.jar

ROOT CAUSE:
-----------
The project was designed for Java 6/7 but is being built with Java 11 (OpenJDK 11.0.27).

In Java 8 and earlier, the JDK's compiler API and annotation processing tools were packaged in a separate file called tools.jar located at $JAVA_HOME/lib/tools.jar.

In Java 9+, these tools were modularized and integrated into the JDK itself as modules (jdk.compiler, etc.), and tools.jar no longer exists.

The build fails because:
1. The compile-testing:0.7 test dependency (used by auto-common module) declares a system-scoped dependency on com.sun:tools:jar
2. This dependency references ${toolsjar} property which points to ${java.home}/../lib/tools.jar
3. The profile that sets this property activates when the file exists: <exists>${java.home}/../lib/tools.jar</exists>
4. On Java 11, this file doesn't exist, so the property gets set but points to a non-existent path
5. Maven tries to resolve the system dependency and fails because the file is missing

AFFECTED FILES:
---------------
1. /home/travis/build/failed/google/auto/pom.xml (parent pom with tools.jar profile)
2. All child modules inheriting from this parent, specifically:
   - auto-common/pom.xml (uses compile-testing:0.7 which requires tools.jar)
   - auto-factory/pom.xml (likely has same issue)
   - auto-value/pom.xml (uses compile-testing:0.6 which likely has same issue)
   - auto-service/pom.xml

FIX STRATEGY:
-------------
There are two approaches to fix this:

APPROACH 1 (Recommended): Add Java 9+ profile to skip tools.jar dependency
- Add a new profile in the parent pom.xml that activates on Java 9+
- This profile should set toolsjar to a dummy value or use a different approach
- The system dependency on tools.jar should be made optional or excluded for Java 9+

APPROACH 2: Upgrade compile-testing library
- Upgrade compile-testing from version 0.7 to a newer version that supports Java 9+
- However, this may not be available for this old codebase

IMPLEMENTATION PLAN:
--------------------
We will use APPROACH 1 with the following changes:

1. Modify /home/travis/build/failed/google/auto/pom.xml:
   - Add a new profile that activates when tools.jar does NOT exist
   - Set the toolsjar property to point to a valid path or use JDK 9+ approach
   - Add a profile specifically for Java 9+ that handles the absence of tools.jar

The fix will involve adding a Java 9+ compatible profile that either:
   a) Makes the tools.jar dependency optional/provided when using Java 9+
   b) Points to an alternative that works with the modular JDK

Since system-scoped dependencies cannot be easily made optional, the best approach is to add a profile that activates on JDK 9+ and does not set the toolsjar property, or sets it to a value that makes Maven skip the resolution.

DETAILED FIX:
-------------
Add a new profile to pom.xml that activates on JDK 9+ and provides an empty or valid toolsjar path.
The profile will use JDK version detection to activate only when running on Java 9 or higher.
