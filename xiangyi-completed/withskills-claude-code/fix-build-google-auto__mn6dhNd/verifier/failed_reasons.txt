# Build Error Analysis for Google Auto Project

## Error Found
Build failure in module: com.google.auto:auto-common:jar:1.0-SNAPSHOT

Error message:
"Could not resolve dependencies for project com.google.auto:auto-common:jar:1.0-SNAPSHOT: Could not find artifact com.sun:tools:jar:11.0.27 at specified path /usr/lib/jvm/java-11-openjdk-amd64/../lib/tools.jar"

## Root Causes

### Issue 1: Parent Version Mismatch
- Root pom.xml (pom.xml) has version: 4-SNAPSHOT
- All module pom.xml files (common, factory, service, value) reference parent version: 3
- This causes Maven to download an older version (3) of the parent from Maven Central instead of using the local version

### Issue 2: Tools.jar Dependency Profile Issue
- The parent pom.xml uses a profile-based approach to handle tools.jar dependency (default-profile and mac-profile)
- These profiles check for the existence of tools.jar at specific locations
- In Java 11+, tools.jar doesn't exist at the traditional location (/usr/lib/jvm/java-11-openjdk-amd64/../lib/tools.jar)
- The tools.jar classes are now part of the Java standard library itself in Java 9+
- The compile-testing dependency transitively requires tools.jar
- Since the profile activation fails (file doesn't exist), the toolsjar property is not set
- This causes the build to fail when trying to resolve dependencies that require tools.jar

## Fixes Required

### Fix 1: Update all module pom.xml files to reference parent version 4-SNAPSHOT
- File: common/pom.xml - change parent version from 3 to 4-SNAPSHOT
- File: factory/pom.xml - change parent version from 3 to 4-SNAPSHOT
- File: service/pom.xml - change parent version from 3 to 4-SNAPSHOT
- File: value/pom.xml - change parent version from 3 to 4-SNAPSHOT

### Fix 2: Update parent pom.xml profile configuration
- Add a new profile for Java 9+ that doesn't require tools.jar
- Or modify the profile activation to handle missing tools.jar gracefully
- For Java 11+, the tools classes are in java.compiler module, which is automatically available

## Solution Applied
The simplest and most effective solution is to:
1. Update all child modules to use parent version 4-SNAPSHOT instead of 3
2. Optionally update the parent pom to handle Java 9+ without requiring tools.jar (but the version fix alone should work since auto-common doesn't actually need tools.jar at compile time - it's only the profile check that's problematic)
