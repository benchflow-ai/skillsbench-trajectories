ARROW LIBRARY - FUZZING NOTES
==============================

Library Overview:
- Arrow is a Python date/time library
- Provides parsing, formatting, and manipulation of dates/times
- Key modules: parser.py, formatter.py, arrow.py, factory.py

High-Value Fuzzing Targets:
----------------------------

1. arrow.parser.DateTimeParser.parse()
   Location: /app/arrow/arrow/parser.py
   Why: Parses user-supplied date/time strings with complex regex patterns
   Input: String datetime representations in various formats
   Risk: Parser vulnerabilities, ReDoS, crashes on malformed input
   Test Focus:
   - Malformed datetime strings
   - Edge cases (leap years, timezone boundaries)
   - Very long strings
   - Invalid Unicode sequences
   - Format string injection

2. arrow.arrow.Arrow.get()
   Location: /app/arrow/arrow/api.py and arrow.py
   Why: Main entry point for creating Arrow objects from various inputs
   Input: Strings, timestamps, datetime objects
   Risk: Type confusion, parsing errors
   Test Focus:
   - Various input types (str, int, float, datetime)
   - Edge timestamp values (negative, very large)
   - Timezone strings
   - Invalid format strings

3. arrow.arrow.Arrow.format()
   Location: /app/arrow/arrow/arrow.py
   Why: Formats Arrow objects according to format strings
   Input: Format strings
   Risk: Format string bugs, crashes on invalid patterns
   Test Focus:
   - Invalid format tokens
   - Very long format strings
   - Special characters in format strings

4. arrow.factory.ArrowFactory.get()
   Location: /app/arrow/arrow/factory.py
   Why: Factory method with multiple input types
   Input: Various datetime representations
   Risk: Type confusion, parsing vulnerabilities
   Test Focus:
   - Mixed type inputs
   - Invalid combinations of arguments

5. arrow.parser.DateTimeParser._parse_multiformat()
   Location: /app/arrow/arrow/parser.py
   Why: Tries multiple formats, complex logic
   Input: Datetime string and list of formats
   Risk: Performance issues (trying many formats), parser bugs
   Test Focus:
   - Large number of formats to try
   - Conflicting format patterns
   - Edge cases that match partially

Additional Test Considerations:
--------------------------------
- Locale-specific parsing (locales.py has extensive locale data)
- Timezone handling edge cases
- ISO 8601 format parsing
- Humanize function with various locales
- Range and span operations
- Arithmetic operations (shift, replace)

Oracle Strategies:
------------------
- No crashes on any input
- Valid inputs should produce consistent results
- Round-trip: parse(format(x)) should preserve semantics
- Timezone conversions should be reversible
- Comparison operations should be transitive

Dependencies to Install:
------------------------
- python-dateutil (check requirements/)
- Standard library only otherwise
