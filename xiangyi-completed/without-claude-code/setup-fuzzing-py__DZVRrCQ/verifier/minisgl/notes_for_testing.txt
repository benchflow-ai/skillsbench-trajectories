LIBRARY OVERVIEW
================================================================================
MiniSGL is a lightweight LLM (Large Language Model) inference serving framework.
It provides an OpenAI-compatible API server for text generation using models
like Llama and Qwen3. The library is designed for tensor-parallel inference
on GPUs with support for KV-cache management, attention backends (FlashInfer,
FlashAttention), and asynchronous message passing via ZeroMQ.

Version: 0.1.0
Python: >=3.10
License: MIT


KEY MODULES AND THEIR PURPOSES
================================================================================

1. minisgl.message (Message Serialization)
   Location: /app/minisgl/python/minisgl/message/
   Purpose: Handles serialization/deserialization of messages between components
   Files:
   - utils.py: Core serialization functions (serialize_type, deserialize_type)
   - backend.py: Backend message classes (UserMsg, ExitMsg, BatchBackendMsg)
   - frontend.py: Frontend message classes (UserReply, BatchFrontendMsg)
   - tokenizer.py: Tokenizer messages (TokenizeMsg, DetokenizeMsg)

2. minisgl.server (API Server)
   Location: /app/minisgl/python/minisgl/server/
   Purpose: FastAPI-based HTTP API server with OpenAI-compatible endpoints
   Files:
   - api_server.py: HTTP endpoint handlers, request/response models
   - args.py: Command-line argument parsing
   - launch.py: Server launch utilities

3. minisgl.tokenizer (Tokenization)
   Location: /app/minisgl/python/minisgl/tokenizer/
   Purpose: Text tokenization and detokenization
   Files:
   - tokenize.py: TokenizeManager class for text-to-tokens
   - detokenize.py: DetokenizeManager class for tokens-to-text
   - server.py: Tokenizer worker process

4. minisgl.models (Model Loading)
   Location: /app/minisgl/python/minisgl/models/
   Purpose: Model weight loading and configuration
   Files:
   - weight.py: Safetensors file loading, weight sharding
   - config.py: ModelConfig and RotaryConfig dataclasses
   - llama.py, qwen3.py: Model-specific implementations

5. minisgl.utils (Utilities)
   Location: /app/minisgl/python/minisgl/utils/
   Purpose: Common utilities including message queues, logging, hardware detection
   Files:
   - mp.py: ZeroMQ message queue wrappers with msgpack serialization
   - hf.py: HuggingFace config loading
   - logger.py: Logging utilities
   - registry.py: Generic registry pattern

6. minisgl.llm (Offline LLM Interface)
   Location: /app/minisgl/python/minisgl/llm/
   Purpose: High-level LLM generation interface for offline use
   Files:
   - llm.py: LLM class with generate() method

7. minisgl.core (Core Data Structures)
   Location: /app/minisgl/python/minisgl/core.py
   Purpose: Core dataclasses for requests, batches, sampling parameters

8. minisgl.env (Environment Variables)
   Location: /app/minisgl/python/minisgl/env.py
   Purpose: Environment variable parsing with type coercion

FUZZING RECOMMENDATIONS
================================================================================

1. HIGHEST VALUE TARGETS:
   - deserialize_type() and _deserialize_any() with malformed msgpack data
   - Tensor buffer handling with mismatched dtype/length
   - ZmqPullQueue.decode() with crafted payloads

2. SETUP FOR FUZZING:
   - The message serialization can be fuzzed standalone without GPU
   - Create mock cls_map dictionaries for deserialize_type testing
   - Generate msgpack payloads directly for mp.py functions

3. FUZZING STRATEGY:
   a) Structure-aware fuzzing for nested dict/list structures
   b) Buffer mutation for tensor data
   c) Type field fuzzing (__type__ values)
   d) Integer boundary testing for numeric parameters
   e) Unicode stress testing for tokenization

4. EXAMPLE HARNESS INPUTS:

   For deserialize_type:
   {
       "__type__": "Tensor",
       "buffer": b"\x00\x01\x02\x03",
       "dtype": "torch.float32"  # mismatch: 4 bytes but float32 needs multiples of 4
   }

   For TokenizeMsg:
   {
       "__type__": "TokenizeMsg",
       "uid": -1,  # negative uid
       "text": "A" * 10000000,  # very long string
       "sampling_params": {...}
   }

5. ENTRY POINTS FOR INTEGRATION TESTING:
   - POST /generate endpoint
   - POST /v1/chat/completions endpoint
   - ZeroMQ IPC addresses (zmq_frontend_addr, zmq_tokenizer_addr)


SECURITY NOTES
================================================================================
- Message deserialization uses dynamic type lookup via globals() which could
  be exploited if attacker controls __type__ field
- Tensor deserialization uses getattr(np, dtype_str) which could access
  arbitrary numpy attributes if dtype_str is not validated
- No apparent input validation on buffer size vs dtype in tensor deserialization
- Path handling in model loading could be vulnerable to path traversal
