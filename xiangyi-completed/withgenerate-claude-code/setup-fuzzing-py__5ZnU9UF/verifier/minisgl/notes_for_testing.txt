# MiniSGL Library - Testing Notes

## Library Purpose
Mini-SGLang is a lightweight yet high-performance inference framework for Large Language Models (LLMs). It's a compact implementation of SGLang designed for LLM serving with advanced optimizations like radix cache, chunked prefill, and tensor parallelism.

## Main Module/Package
- Import path: `import minisgl`
- Main components: Engine, Scheduler, Server modules
- Core classes: `Req`, `SamplingParams`, various backend implementations

## High-Priority Functions for Fuzzing

### 1. SamplingParams validation
- **Location**: `minisgl.core.SamplingParams`
- **Purpose**: Configuration for text generation sampling
- **Input types**: floats (temperature, top_p), ints (top_k, max_tokens), bool
- **Edge cases**:
  - Negative values
  - Very large values
  - Invalid combinations
  - Out of range parameters
- **Exceptions**: ValueError, AssertionError
- **Why fuzz**: Configuration parsing with numeric bounds

### 2. Message handling / Serialization
- **Location**: `minisgl.message` module
- **Purpose**: Handle inter-process communication with msgpack
- **Input types**: bytes (serialized messages)
- **Edge cases**:
  - Malformed msgpack data
  - Very large messages
  - Invalid message structures
- **Exceptions**: msgpack errors, ValueError
- **Why fuzz**: Deserializes external data - security critical

### 3. Request creation
- **Location**: `minisgl.core.Req` and engine request handling
- **Purpose**: Create and validate inference requests
- **Input types**: tensors, configuration dicts
- **Edge cases**:
  - Invalid tensor shapes
  - Out of bounds indices
  - Inconsistent lengths
- **Exceptions**: AssertionError, ValueError
- **Why fuzz**: Complex validation logic

### 4. Config parsing
- **Location**: `minisgl.engine.config` module
- **Purpose**: Parse engine configuration
- **Input types**: dict/JSON configuration
- **Edge cases**:
  - Missing required fields
  - Invalid types
  - Conflicting settings
- **Exceptions**: ValueError, KeyError
- **Why fuzz**: Configuration parsing is error-prone

### 5. Server API endpoints
- **Location**: `minisgl.server` module (FastAPI endpoints)
- **Purpose**: Handle HTTP API requests
- **Input types**: JSON payloads
- **Edge cases**:
  - Malformed JSON
  - Invalid parameters
  - Very large requests
- **Exceptions**: Validation errors
- **Why fuzz**: External input from network

## Dependencies
- torch (PyTorch)
- transformers>=4.56.0
- msgpack (message serialization)
- fastapi, uvicorn (web server)
- sgl_kernel, flashinfer-python (GPU kernels)
- Many others (heavy ML stack)

## Known Issues
- Heavy dependencies (torch, transformers) - slow to import
- GPU-specific code may not work without CUDA
- Complex initialization requirements
- Linux-only support

## Testing Strategy
1. Focus on data parsing/validation, NOT GPU/model code
2. Primary targets:
   - Configuration parsing and validation
   - Message serialization/deserialization
   - Parameter validation
3. Avoid:
   - GPU operations (require CUDA)
   - Model loading (too slow, requires resources)
   - Actual inference (too complex)
4. Test with:
   - Invalid configurations
   - Malformed serialized data
   - Out-of-range parameters
5. Catch expected exceptions: ValueError, KeyError, msgpack errors
6. Let unexpected exceptions crash (bugs!)
7. May need to mock/skip GPU-dependent initialization
