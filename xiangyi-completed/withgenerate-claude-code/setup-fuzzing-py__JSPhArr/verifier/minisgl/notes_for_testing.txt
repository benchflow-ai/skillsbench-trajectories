# Testing Notes: Mini-SGLang

## Overview
Mini-SGLang is a lightweight LLM (Large Language Model) inference framework with advanced optimizations. It's a compact implementation focused on high-performance serving of language models.

## Main Package Structure
- Main module: python/minisgl/
- Core files: core.py (data structures), engine/, scheduler/, server/
- Key functionality: LLM inference, request scheduling, KV caching

## Key Public APIs

### 1. SamplingParams
- **Location**: python/minisgl/core.py:15
- **Purpose**: Parameters for text generation sampling
- **Input types**: temperature (float), top_k (int), top_p (float), max_tokens (int)
- **Potential issues**: Invalid parameter ranges, negative values, extreme values
- **Why fuzz**: Configuration parsing, parameter validation

### 2. Req (Request)
- **Location**: python/minisgl/core.py:28
- **Purpose**: Represents an inference request
- **Input types**: torch.Tensor (input_ids), various integers
- **Potential issues**: Invalid tensor shapes, negative indices, out-of-range values
- **Why fuzz**: Core data structure for requests

### 3. Message/Protocol Handling
- **Location**: python/minisgl/message/
- **Purpose**: Network message serialization/deserialization
- **Input types**: Binary data (msgpack), JSON
- **Potential issues**: Malformed messages, buffer overflows, protocol violations
- **Why fuzz**: Network input handling

### 4. Server Endpoints
- **Location**: python/minisgl/server/
- **Purpose**: FastAPI endpoints for HTTP requests
- **Input types**: JSON payloads, HTTP requests
- **Potential issues**: Malformed JSON, missing fields, type mismatches
- **Why fuzz**: External API input

## Functions for Fuzzing Priority

### High Priority
1. **Message deserialization** - Network protocol handling
   - Parses msgpack/JSON from network
   - High attack surface
   - Handles untrusted input

2. **SamplingParams validation** - Parameter parsing
   - Accepts user configuration
   - Range validation
   - Type checking

3. **Request creation/validation** - Input validation
   - Validates request parameters
   - Tensor shape checking
   - Range validation

### Medium Priority
1. **Configuration parsing** - Config file handling
2. **Tokenizer input** - Text encoding
3. **API endpoint handlers** - HTTP request processing

## Dependencies to Install
- Required: torch, transformers, msgpack, fastapi, uvicorn, sgl_kernel, flashinfer-python,
  accelerate, pyzmq, prompt_toolkit, openai, apache-tvm-ffi
- Optional: pytest (for testing)
- Note: Many dependencies are CUDA-specific and Linux-only

### Expected Exceptions
- `AssertionError`: Validation failures
- `ValueError`: Invalid parameter values
- `TypeError`: Type mismatches
- `RuntimeError`: CUDA/torch errors
- `msgpack.exceptions.*`: Deserialization errors

## Edge Cases to Consider
- Negative temperature/top_p values
- Zero or negative max_tokens
- Very large max_tokens (memory exhaustion)
- Invalid top_k values (0, negative)
- Extreme float values (inf, nan)
- Empty tensors
- Mismatched tensor shapes
- Invalid device specifications
- Malformed msgpack data
- Unicode in string fields
- Missing required fields

## Fuzzing Strategy
**Note**: This library has heavy dependencies (CUDA, torch, transformers) that may not be available in fuzzing environment.

Focus on lightweight components:
1. **SamplingParams** - Pure Python dataclass with validation
2. **Data structure creation** - Parameter validation
3. **Utility functions** - If any exist for parsing/validation

Avoid fuzzing:
- CUDA-dependent code (requires GPU)
- Model loading (requires large files)
- Network server (requires setup)

The fuzzer should test:
- Parameter validation logic
- Data structure invariants
- Range checking
- Type validation
- Simple serialization/deserialization if possible

## Special Considerations
- Library requires CUDA and may not run in CPU-only environment
- Many dependencies may be difficult to install
- Focus on testing parameter validation and data structure creation
- Skip GPU-dependent functionality
