TARGET 1: Message Serialization/Deserialization (HIGHEST PRIORITY)
------------------------------------------------------------------------

File: /app/minisgl/python/minisgl/message/utils.py

Functions:
  - serialize_type(self) -> Dict
  - deserialize_type(cls_map: Dict[str, Type], data: Dict) -> Any
  - _serialize_any(value: Any) -> Any
  - _deserialize_any(cls_map: Dict[str, Type], data: Any) -> Any

Why good fuzz targets:
  These functions handle custom serialization and deserialization of arbitrary
  Python objects using msgpack over ZMQ. The deserialization path is
  particularly interesting because:
  1. It takes untrusted dict input and reconstructs Python objects by looking
     up class names in a cls_map and calling cls(**kwargs).
  2. It uses getattr(np, dtype_str) to dynamically resolve numpy dtypes from
     a string, which could be abused with unexpected dtype strings.
  3. It calls np.frombuffer() on raw bytes, where mismatched dtype and buffer
     size could cause issues.
  4. It recursively processes nested dicts, lists, and tuples.

Input types:
  - deserialize_type: cls_map is a Dict[str, Type], data is a Dict with a
    "__type__" key (str) and arbitrary other keys.
  - For Tensor deserialization: data = {"__type__": "Tensor", "buffer": bytes,
    "dtype": str}
  - For object deserialization: data = {"__type__": str, key: value, ...}

Acceptable exceptions:
  - KeyError (missing class in cls_map)
  - TypeError (wrong constructor arguments)
  - AssertionError (from "assert self.dim() == 1" or "assert isinstance(buffer, bytes)")

Suspicious exceptions:
  - SegFault / memory corruption from np.frombuffer with mismatched dtype/size
  - AttributeError from getattr(np, dtype_str) with malicious dtype strings
  - Arbitrary code execution if cls_map contains dangerous types
  - Infinite recursion from deeply nested structures
  - Unhandled exceptions from unexpected data types

Dependencies needed:
  - numpy
  - torch
  - msgpack (for the full pipeline)

Fuzz approach:
  1. Direct fuzzing of deserialize_type with crafted dicts.
  2. Full round-trip: msgpack.unpackb(fuzz_bytes) -> deserialize_type.
  3. Focus on the Tensor path: vary dtype string and buffer bytes.

TARGET 2: msgpack Deserialization Pipeline (HIGH PRIORITY)
------------------------------------------------------------------------

File: /app/minisgl/python/minisgl/utils/mp.py

Functions:
  - ZmqPullQueue.get() -> T          (line 66-68)
  - ZmqPullQueue.decode(raw: bytes) -> T   (line 73-74)

Why good fuzz targets:
  These functions perform: msgpack.unpackb(bytes, raw=False) -> decoder(dict).
  The decoder functions are BaseFrontendMsg.decoder, BaseBackendMsg.decoder,
  BaseTokenizerMsg.decoder, and BatchTokenizerMsg.decoder. All of these call
  deserialize_type(globals(), json) which uses the module's globals() as the
  class registry -- meaning any class in that module's namespace can be
  instantiated. Malformed msgpack payloads could cause unexpected behavior.

Input types:
  - Raw bytes (msgpack-encoded data)

Acceptable exceptions:
  - msgpack.exceptions.UnpackException (malformed msgpack)
  - KeyError, TypeError (invalid message structure)

Suspicious exceptions:
  - Memory corruption, segfaults
  - Uncontrolled object instantiation
  - Resource exhaustion from large allocations

Dependencies needed:
  - msgpack
  - zmq (but can be bypassed by calling decode() directly)

Fuzz approach:
  Can bypass ZMQ entirely and fuzz: msgpack.unpackb(data) then pass to
  BaseBackendMsg.decoder(), BaseFrontendMsg.decoder(), BaseTokenizerMsg.decoder().

------------------------------------------------------------------------

File: /app/minisgl/python/minisgl/message/backend.py

Functions:
  - BaseBackendMsg.decoder(json: Dict) -> BaseBackendMsg   (static method, line 17-19)

Why good fuzz target:
  This decoder is the entry point for all messages from the tokenizer to
  the scheduler backend. It calls deserialize_type(globals(), json) where
  globals() includes: BaseBackendMsg, BatchBackendMsg, ExitMsg, UserMsg,
  SamplingParams, torch, and other imports. The UserMsg dataclass expects
  uid (int), input_ids (torch.Tensor), and sampling_params (SamplingParams),
  so the deserializer must reconstruct nested objects including tensors.

Input types:
  - Dict with "__type__" key and nested fields

Acceptable exceptions:
  - KeyError (unknown __type__)
  - TypeError (wrong constructor args)
  - AssertionError

Suspicious exceptions:
  - Buffer overflows from malformed tensor data
  - Arbitrary object instantiation

Fuzz approach:
  Generate dicts with various "__type__" values and nested structures.
  Focus on UserMsg with malformed input_ids tensor data.

TARGET 6: Radix Cache Tree Operations (MEDIUM-HIGH PRIORITY)
------------------------------------------------------------------------

File: /app/minisgl/python/minisgl/kvcache/radix_manager.py

Functions:
  - RadixCacheManager.match_prefix(input_ids: torch.Tensor) -> Tuple[RadixCacheHandle, torch.Tensor]
  - RadixCacheManager.insert_prefix(input_ids: torch.Tensor, indices: torch.Tensor) -> int
  - RadixCacheManager.evict(size: int) -> torch.Tensor
  - RadixCacheManager._walk(input_ids: torch.Tensor) -> Tuple[RadixTreeNode, int]
  - RadixTreeNode._split_at(pos: int) -> RadixTreeNode
  - RadixTreeNode.get_match_len(input_ids: torch.Tensor) -> int
  - RadixCacheManager.lock_handle(handle, unlock=False) -> None

Why good fuzz targets:
  The radix tree is a complex data structure that manages KV cache prefix
  sharing. It involves tree walking, node splitting, reference counting,
  and eviction with a heap. Sequences of operations (insert, match, evict,
  lock/unlock) with varied input_ids tensors can expose:
  1. Reference counting bugs (negative ref_count, leaked references)
  2. Tree corruption during split operations
  3. Eviction logic errors (evicting protected nodes)
  4. Integer overflow in size tracking (evictable_size, protected_size)
  5. Issues with the fast_compare_key C++ kernel

Input types:
  - input_ids: 1D torch.Tensor of int32 (token IDs)
  - indices: 1D torch.Tensor of int32 (page indices)
  - size: int (for eviction)

Acceptable exceptions:
  - AssertionError (e.g., "Cannot evict {size}")
  - NotImplementedError (from reset())

Suspicious exceptions:
  - Segfaults from fast_compare_key C++ code
  - Inconsistent tree state after operations
  - ref_count going negative
  - evictable_size/protected_size becoming inconsistent

Dependencies needed:
  - torch (CPU tensors only, no GPU needed)
  - The fast_compare_key kernel (from tvm_ffi, requires compilation)

Fuzz approach:
  Create a RadixCacheManager, then perform sequences of match_prefix,
  insert_prefix, lock_handle, evict operations with random input_ids
  tensors. After each sequence, call check_integrity().
  NOTE: fast_compare_key requires C++ compilation; if unavailable, can mock
  it for pure-Python fuzzing.

TARGET 7: Detokenize Manager - Incremental Decoding (MEDIUM PRIORITY)
------------------------------------------------------------------------

File: /app/minisgl/python/minisgl/tokenizer/detokenize.py

Functions:
  - DetokenizeManager.detokenize(msgs: List[DetokenizeMsg]) -> List[str]
  - find_printable_text(text: str) -> str
  - _is_chinese_char(cp: int) -> bool

Why good fuzz targets:
  1. detokenize() manages stateful incremental decoding with surrogate
     handling, read offsets, and sent offsets. Complex state transitions
     with various token sequences could expose off-by-one errors or
     inconsistent state.
  2. find_printable_text() handles Unicode edge cases (CJK characters,
     replacement characters).
  3. The interaction between batch_decode and the surrogate/read offset
     logic could produce unexpected results with adversarial token sequences.

Input types:
  - List[DetokenizeMsg] where DetokenizeMsg has uid (int), next_token (int),
    finished (bool)

Acceptable exceptions:
  - IndexError (from empty text slicing edge cases)

Suspicious exceptions:
  - State corruption in decode_map
  - Memory leaks (uid never cleaned up if finished never sent)
  - Unicode errors

Dependencies needed:
  - transformers (AutoTokenizer)

Fuzz approach:
  Create a DetokenizeManager with a real tokenizer, then send sequences of
  DetokenizeMsg with various token IDs (including EOS, special tokens, and
  out-of-vocabulary IDs). Vary uid patterns (reuse, never finish, etc.).

================================================================================
RECOMMENDED FUZZING PRIORITY ORDER
================================================================================

1. deserialize_type / _deserialize_any (Target 1)
   - Highest risk: processes untrusted data, dynamic object instantiation,
     unsafe numpy operations. Pure CPU, no GPU needed.

2. Full msgpack -> decoder pipeline (Target 2)
   - Feed raw bytes through msgpack.unpackb then through decoders.
     Tests the full attack surface of the serialization layer.

3. BaseBackendMsg.decoder (Target 3)
   - Focuses on the most complex message type (UserMsg with tensors).

4. BaseTokenizerMsg.decoder (Target 4)
   - Similar to Target 3 but for tokenizer messages.

5. find_printable_text (Target 8)
   - Pure function, easy to fuzz, tests Unicode handling.

6. _PARSE_MEM_BYTES (Target 10)
   - Pure function, easy to fuzz, parses user input strings.

7. RadixCacheManager operations (Target 6)
   - Stateful fuzzing of tree operations. Requires C++ kernel or mocking.

8. DetokenizeManager.detokenize (Target 7)
   - Stateful fuzzing with token sequences. Requires a tokenizer model.

9. SamplingParams (Target 9)
   - Simple construction fuzzing.

10. OpenAI API models (Target 11)
    - Pydantic validation fuzzing.
